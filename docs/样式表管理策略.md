# RoxCSS 样式表管理方案

## 决策记录

经过讨论与实测，确定以下原则：

- **不使用 `insertRule`**：P0 实测证明其在"插入-强制重算交替"场景下会退化为 O(N²)
- **唯一实现为滚动 `<style>` 桶**：活动 `<style>` 元素复用，单桶规则数上限 1000，冻结后新建
- **批量规则通过一次文本赋值写入**：`textContent` 整体重写，不是逐条插入
- **同步语义**：`rox` 调用返回时，规则已生效
- **不采用 `adoptedStyleSheets`**：容器数量随 flush 次数线性增长，DevTools 面板堆积导致调试卡顿（弃用详情见下）
- **单桶上限 1000 已实测定案**（2026-09-02）：规则上万时 Elements 面板仍流畅，无调参需求（权衡见"阈值"节）

---

## 方案沿革

| 方案      | 容器                                                          | 容器数量              | 结局                                                       |
| --------- | ------------------------------------------------------------- | --------------------- | ---------------------------------------------------------- |
| A（早期） | 每次 flush 新建 `<style>`                                     | = flush 次数          | 弃：Elements 面板堆积大量 style 标签                       |
| B（中期） | 每次 flush 新建 `CSSStyleSheet`，push 到 `adoptedStyleSheets` | = flush 次数          | 弃：Adopted Style Sheets 区同样堆积，DevTools 面板严重卡顿 |
| C（最终） | 滚动 `<style>` 桶（满 1000 冻结新建）                         | ceil(总规则数 / 1000) | 当前实现                                                   |

**核心教训**：容器数量 = flush 次数的方案，无论容器是 DOM 节点还是 adopted stylesheet，都会在 DevTools 的某一区域线性堆积。渐进渲染的应用里每次 `rox` 调用都可能产生新规则，规则上万时容器数以千计——**页面运行时无卡顿，卡的是控制台面板**（DevTools 对容器数量的渲染与追踪成本）。方案 C 将容器数量收敛为规则数 / 1000，是当前决策的直接动因。

---

## 方案 C：`<style>` 滚动桶（最终方案）

### 模型

```
rox 调用 → 收集新规则到 batch
  → 检查活动桶是否有空间（≤1000 条）
  → 有空间：追加到活动桶规则数组，整体 textContent 重写
  → 无空间（或首次）：冻结当前桶，新建 <style data-roxcss> 作为活动桶
```

### 实现

`src/dom.ts`（当前实现，简化示意）：

```typescript
export const MAX_BUCKET_RULES = 1000;

/** 活动滚动桶：el 为 head 中的 <style>，rules 为其文本镜像 */
interface Bucket {
  el: StyleElementLike;
  rules: string[];
}

let bucket: Bucket | null = null;

/** 在 head 挂一个新的 <style> 作为活动桶 */
function openBucket(doc: DocumentLike, head: HeadLike): Bucket {
  const el = doc.createElement("style");
  el.setAttribute("data-roxcss", "");
  head.appendChild(el);
  return { el, rules: [] };
}

/** 整体重写活动桶文本（一次解析 + 一次样式失效） */
function rewrite(b: Bucket) {
  b.el.textContent = b.rules.join("\n");
}

export function flushStyles(rules: string[]): void {
  if (rules.length === 0) return;
  const doc = getDocument();
  if (!doc) return;
  const head = doc.head;
  if (!head) return;

  // 首次调用或活动桶已满：冻结当前桶，开新桶
  if (!bucket || bucket.rules.length === MAX_BUCKET_RULES) {
    bucket = openBucket(doc, head);
  }

  // 主路径（绝大多数调用）：本批全部放得下——追加后整体重写
  const room = MAX_BUCKET_RULES - bucket.rules.length;
  if (rules.length <= room) {
    bucket.rules.push(...rules);
    rewrite(bucket);
    return;
  }

  // 罕见路径：单批跨桶——填满当前桶，剩余部分交给新桶继续
  bucket.rules.push(...rules.slice(0, room));
  rewrite(bucket);
  flushStyles(rules.slice(room));
}
```

要点：

- **冻结即不重写**：旧桶冻结后不再触碰，单次重写成本只与活动桶内规则数有关
- **单批跨桶拆分**：主路径直线返回，跨桶（单批超过剩余空间）时填满当前桶、剩余递归交给新桶，任何桶都不超过上限（递归深度 ≈ 跨桶次数，新桶后每层至少装 1000 条，无栈溢出风险）
- **无 DOM 跳过**：SSR/测试环境规则仅记录在内存，`getCSS()` 可读，样式不生效
- **调参入口**：`MAX_BUCKET_RULES` 为 `src/dom.ts` 顶部常量，改一处即可

### 性能特征

| 操作         | 成本                                                    |
| ------------ | ------------------------------------------------------- |
| 追加新规则   | O(batch 大小) + 一次活动桶 textContent 重写（≤1000 条） |
| 单次重写解析 | O(活动桶规则数) ≤ O(1000)                               |
| 样式失效     | 每次 flush 1 次                                         |
| 已有规则影响 | 无（旧桶冻结，不重写）                                  |
| P0 退化风险  | 无（整体替换，非逐条 insertRule）                       |
| 容器数量     | ceil(总规则数 / 1000)                                   |

**阈值 1000 的权衡**：

| 维度                     | 数值                     |
| ------------------------ | ------------------------ |
| 单次重写解析成本         | 量级 <0.1ms（1000 条内） |
| 最坏同步重算（80 元素）  | 量级 ~7ms                |
| 最坏同步重算（500 元素） | 量级 ~47ms               |
| 1 万规则时的容器数       | 10 个                    |
| 5 万规则时的容器数       | 50 个                    |

阈值偏大 → 单桶重写与重算成本上升；偏小 → 容器数量增多，DevTools 噪音回升。

**实测结论（2026-09-02）**：浏览器实测规则上万时，`<style data-roxcss>` 数量可控、Elements 面板流畅无卡顿，**1000 阈值定案**。如后续场景需要调整，改 `MAX_BUCKET_RULES`（`src/dom.ts` 顶部常量）一处即可。

### 兼容性

`<style>` + `textContent` 是所有浏览器都支持的基础能力，无版本门槛，无需特性检测。

---

## 为什么不用 insertRule

P0 实测（见 docs/性能分析.md）：逐条 `insertRule` 在"插入-强制重算交替"场景下，200 条规则插入耗时从 1.7ms 恶化到 708~1160ms（随已有规则数线性增长）。批量写入把 N 次样式失效降为 1 次。`textContent` 整体替换与 `replaceSync` 在这一点上等价（一次解析 + 一次失效），而前者不需要构造样式表能力。

## 测试策略

- **Node 环境（mock DOM）**：滚动桶行为——首 flush 建桶、未满追加重写、满 1000 冻结新建、单批跨桶拆分、规则顺序连续、空批次跳过、无 document/head 跳过（`tests/dom.test.ts`）
- **Node 环境**：token 解析、matcher 查找、缓存、getCSS（无 DOM，规则仅内存记录）
- **浏览器**：调用后立即 `getComputedStyle` 验证同步生效（同步语义回归）
- **P0 回归**：插入-强制重算-插入交替场景，确认无退化（example 测量面板的"生成报告"内置此场景）
- **阈值**：1000 已浏览器实测定案（2026-09-02，见"阈值"节）；如需调整，改 `MAX_BUCKET_RULES` 一处并回归上述用例

# RoxCSS 样式表管理方案

## 决策记录

经过讨论与实测，确定以下原则：

- **不使用 `insertRule`**：P0 实测证明其在"插入-强制重算交替"场景下会退化为 O(N²)
- **每次 flush 创建一个新的 `CSSStyleSheet`**：通过 `replaceSync` 批量写入，直接 `push` 到 `adoptedStyleSheets`。不滚动、不复用、不设阈值
- **批量规则通过一次文本赋值写入**：`replaceSync` 整体替换，不是逐条插入
- **同步语义**：`rox` 调用返回时，规则已生效
- **仅实现方案 B，不提供回退**：不支持 `adoptedStyleSheets`（可写数组）的环境不在支持范围
- 方案 A（`<style>` 元素）作为早期实现的对照记录保留，已弃用

---

## 方案 A：`<style>` 元素 + `textContent`（早期实现，已弃用）

> 早期版本曾采用本方案，后由方案 B 取代。保留分析记录供对照，不再实现。

### 模型

```
rox 调用 → 收集新规则到 batch → 创建新 <style> → textContent 赋值 → appendChild 到 <head>
```

### 性能特征

| 操作                  | 成本                              |
| --------------------- | --------------------------------- |
| 追加新规则            | O(batch 大小)                     |
| 单次 textContent 解析 | O(该 sheet 内规则数)              |
| 样式失效              | 每次 flush 1 次                   |
| 已有规则影响          | 无（每个 sheet 只含本批规则）     |
| P0 退化风险           | 无（整体替换，非逐条 insertRule） |
| 容器数量              | = flush 次数（有新增的调用次数）  |

### 弃用原因

- 每次 flush 创建 DOM 节点，DevTools 的 Elements 面板堆积 `<style data-roxcss>` 标签
- 方案 B 提供等价的性能特征（O(batch) 写入、每次 1 次失效、无 P0 退化）且零 DOM 节点，结构更简单

## 方案 B：`CSSStyleSheet` + `replaceSync` + 每次新建

### 模型

```
rox 调用 → 收集新规则到 batch → new CSSStyleSheet() → replaceSync(batch.join("\n")) → adoptedStyleSheets.push(sheet)
```

### 核心机制

每次 flush 创建一个全新的 CSSStyleSheet 对象，写入本批规则，直接 push 到 `document.adoptedStyleSheets`。无滚动桶、无阈值、无复用。

### 实现

```typescript
function flush(batch: string[]) {
  const doc = getDocument();
  if (!doc) return;

  const sheet = new CSSStyleSheet();
  sheet.replaceSync(batch.join("\n"));
  doc.adoptedStyleSheets.push(sheet);
}
```

### 性能特征

| 操作         | 成本                                     |
| ------------ | ---------------------------------------- |
| 追加新规则   | O(batch 大小)                            |
| 新建容器成本 | 纯 JS 对象创建 + replaceSync + 数组 push |
| 样式失效     | 每次 flush 1 次                          |
| 已有规则影响 | 无（每个 sheet 只含本批规则）            |
| P0 退化风险  | 无（整体替换，非逐条 insertRule）        |
| 容器数量     | = flush 次数                             |

### 特点

- **零 DOM 节点**：不创建 `<style>` 元素，不触碰 DOM 树
- **DevTools 整洁**：adopted stylesheets 不在 Elements 面板堆积
- **结构最简单**：和当前实现同构，只是容器类型从 DOM 元素换成 JS 对象
- **容器数量线性增长**：`adoptedStyleSheets` 数组本身随调用次数线性增长。DevTools 的 Adopted Style Sheets 区同样堆积，只是从 DOM 节点转移到了数组。运行时性能影响极低

### 兼容性

- **需要 `adoptedStyleSheets` 为可写数组的实现**（约 Chrome 115+，2023 年起；同期 Firefox、Safari）
- 早期实现（Chrome 73–114 等）中 `adoptedStyleSheets` 是 FrozenArray 语义，`push` 会**静默无效**
- **不提供回退**：无 `adoptedStyleSheets`（或为 FrozenArray 语义）的环境不在支持范围

## 方案 B：实现

当前 `src/dom.ts` 的实现即方案 B，无特性检测、无回退：

```typescript
export const adoptStyles = (css: string) => {
  const doc = getDocument();
  if (!doc || !CSSStyleSheetCtor) return;

  const sheet = new CSSStyleSheetCtor();
  sheet.replaceSync(css);
  doc.adoptedStyleSheets.push(sheet);
};
```

- 无 DOM（SSR/测试）或环境中不存在 `CSSStyleSheet` 构造器时跳过写入：规则仅记录在内存，`getCSS()` 可读，样式不生效
- `adoptedStyleSheets` 数组随调用次数线性增长（DevTools 的 Adopted Style Sheets 区堆积），运行时性能影响极低，是刻意接受的取舍

---

## 为什么不用 insertRule

P0 实测（见 docs/性能分析.md）：逐条 `insertRule` 在"插入-强制重算交替"场景下，200 条规则插入耗时从 1.7ms 恶化到 708~1160ms（随已有规则数线性增长）。批量写入把 N 次样式失效降为 1 次。

## 测试策略

- **Node 环境**：token 解析、matcher 查找、缓存、getCSS（无 DOM，规则仅内存记录）
- **浏览器（方案 B）**：Chrome 115+ / 同期 Firefox、Safari（可写 adoptedStyleSheets）
- **同步语义**：调用后立即 `getComputedStyle` 验证生效
- **P0 回归**：插入-强制重算-插入交替场景，确认无退化（example 测量面板的"生成报告"内置此场景）

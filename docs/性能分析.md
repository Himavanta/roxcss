# RoxCSS 性能分析

## 一、性能模型

roxcss 是运行时原子 CSS 引擎，每次调用 `rox\`...\`` 时对每个未缓存 token 执行：

1. 按 `:` 和 `-` 拆分 token，在 matcher 树中查找
2. 生成 CSS 规则文本
3. **调用结束时把本次产生的全部新规则拼成一段文本，经 `adoptStyles` 一次性写入 `adoptedStyleSheets`**（`CSSStyleSheet` + `replaceSync`，见 `src/dom.ts`），保持"调用后立即生效"的同步语义

对页面性能的影响由三个因素决定：

### 1. 插入频率 = 去重后的 token 数，而非调用次数

`injected` / `failed` 两个 `Set` 保证每个 token 只处理一次：

- 同一 token 重复调用（如组件重复渲染）只做字符串拆分 + 查表，不触碰 CSSOM
- 典型页面：初始化时集中插入几十~几百条规则，之后交互期几乎零插入
- 只有动态拼接新类名时才会产生新插入

### 2. 批量写入：一次调用 = 一次解析 + 一次样式失效

早期实现逐条 `insertRule`。浏览器对纯插入通常走懒重算（样式失效被合并为一次），但在**"插入规则 ⇄ 强制读取布局"交替**的场景下（页面在 rox 调用后读取 `offsetHeight`/`getBoundingClientRect`），Chrome 会退化为同步路径——每次 `insertRule` 都同步重算样式，成本 O(N²)（实测 200 条规则插入 700ms+，见下文缺陷记录）。

批量写入把 N 次失效降为 1 次：

- 一次 `rox\`...\`` 调用产生的新规则合并为一段 CSS 文本，`replaceSync` 一次写入（一次解析 + 一次失效）
- 每条规则的写入成本 O(批大小)，不随历史规则数增长
- 同步语义不变：调用返回时规则已生效

> 粒度说明：每次 `rox` 调用结束立即写入（保证同步语义）。频繁生成动态 token 时，尽量**合并到一次模板调用**（空格分隔多个类名）而不是循环多次调用，避免产生多个 sheet 与多次样式失效。
>
> 每个写入批次对应一个新的 `CSSStyleSheet`（`adoptedStyleSheets` 数组增长），零 DOM 节点。

### 3. 规则匹配是主要成本

插入之后，每次样式重算（style recalc）时，DOM 中的每个元素需要遍历 CSS 规则找到匹配项：

- roxcss 使用 `[class~="token"]` 属性选择器（类名即 token，DevTools 可读、无映射表）
- 属性选择器的匹配成本高于 `.class` 选择器，但现代引擎（Blink/Gecko）对常见属性选择器有专门优化
- 总成本 ≈ **规则条数 × 元素数 × 选择器匹配开销**
- 实测：80 个元素的页面、3282 条规则，一次全量重算约 17ms
- 这是所有运行时原子 CSS 方案（Tailwind CDN、UnoCSS 等）共有的代价，不是 roxcss 特有

## 二、测量方法

### 1. Chrome DevTools Performance 面板

录制一次加载 + 交互过程：

- **Recalculate Style**（样式重算）：总时长与发生次数
- **Scripting / Long Tasks**：是否出现插入高峰导致的脚本卡顿
- **Summary** 视图对比 Scripting 与 Rendering 占比

### 2. 代码内精确计时

```ts
function bench(fn: () => unknown, n = 1000) {
  const t0 = performance.now();
  for (let i = 0; i < n; i++) fn();
  console.log(`${n} 次平均 ${((performance.now() - t0) / n).toFixed(3)}ms`);
}

// 冷写入（首次，含解析与 CSSOM 写入）
bench(() => rox`p-4px m-2px w-3px flex-1`);

// 缓存命中（重复调用，应接近 0）
bench(() => rox`p-4px m-2px w-3px flex-1`);
```

首次与重复调用的差距就是写入的真实成本。

> 注意：基准 token 必须生成**合法 CSS**。当前默认 matcher 值原样使用（单位写全，如 `p-4px`）；若自定义 matcher 固定拼接单位（如 `padding:${v}px`），则应写 `p-4`。无效规则会被浏览器静默忽略，测量结果不能代表真实使用。

### 3. 监听长任务

```ts
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (entry.entryType === "longtask") console.log("长任务:", entry);
  }
}).observe({ entryTypes: ["longtask"] });
```

### 4. 对比实验（最可信）

同一页面两个版本：静态 CSS 文件 vs roxcss 运行时插入，对比 LCP / CLS / 总样式重算时长。规则数在几百条量级时差异通常可忽略。

### 5. 压力测试（找边界）

```ts
const t0 = performance.now();
for (let i = 0; i < 5000; i++) {
  rox`p-${i}px w-${i % 50}px flex-1`;
}
console.log("5000 条规则插入耗时:", performance.now() - t0, "ms");

// 触发同步样式重算
const t1 = performance.now();
void document.body.offsetHeight;
console.log("强制样式重算耗时:", performance.now() - t1, "ms");
```

## 三、example 中的测量面板

`packages/example/src/components/PerfPanel.vue` 提供 dev-only 浮层（`import.meta.env.DEV` 控制，生产构建不包含）：

| 指标     | 含义                                           |
| -------- | ---------------------------------------------- |
| 规则数   | 当前 rox 实例已注入的规则条数                  |
| 冷插入   | 一次性注入 200 条新 token 的总耗时             |
| 缓存命中 | 重复调用相同 token 1000 次的耗时               |
| 强制重算 | 插入后触发同步样式重算（`offsetHeight`）的耗时 |

面板有两个按钮：

- **测量**：执行一轮上述基准
- **生成报告**：输出完整文本报告（5 轮插入趋势、重算随规则数增长、长任务、paint 指标），可复制分享。该报告循环的"插入-强制重算交替"正是 P0 的触发场景，用于回归验证

操作方式：

1. `vp dev`（在 `packages/example` 下）启动
2. 页面右下角出现测量面板，点击"测量"或"生成报告"
3. 多次点击可观察持续新增 token 对性能的影响（规则数递增）

## 四、判断标准

| 场景          | 预期                                                                                                |
| ------------- | --------------------------------------------------------------------------------------------------- |
| 规则数 < 1000 | 插入与匹配开销均不可感知，放心使用                                                                  |
| 1000 ~ 10000  | 插入仍快（实测 1.5 万规则时插入 200 条 ~1.6ms）；元素少的页面重算无感（78 元素 × 1.4 万规则 ≈ 5ms） |
| > 10000       | 元素数少时仍健康；**元素密集页面（上千节点）建议拆分实例**                                          |

## 五、缺陷记录

### P0（已修复）：逐条 insertRule 在"插入与强制布局交替"时 O(N²)

- **现象**：一次调用逐条 `insertRule` 插入 200 条规则，插入耗时 1.7ms → 708ms → 850ms → 999ms → 1160ms（随已有规则数线性增长）；插入后读取布局返回 0ms（样式已在插入过程中同步结算）
- **根因**：页面在 rox 调用后读取布局（`offsetHeight`/`getBoundingClientRect`）时，Chrome 从懒重算路径退化为同步路径，每次 `insertRule` 都同步重算，成本 O(规则数 × 元素数)；与 trace 对照确认纯插入场景 200 条规则仅需 ~15ms
- **修复**：调用内批量写入——一次 `rox\`...\``调用收集全部新规则，拼成文本经`replaceSync`一次性写入新`CSSStyleSheet`并 adopt（`src/dom.ts`的`adoptStyles`），N 次样式失效降为 1 次
- **验证（修复前后对比，同一测量面板）**：
  - 插入耗时：1.7 → 708 → 850 → 999 → 1160 ms（修复前）→ **1.1 → 1.0 → 1.2 → 0.9 → 1.0 ms**（修复后，约 700 倍改善且不随规则数增长）
  - 强制重算：0 ms（被插入吞掉）→ 独立显示 2.7 ~ 3.1 ms
  - trace 对照：UpdateLayoutTree 总耗时 89 ms → 7.4 ms，单次重算 ~3 ms → ~0.4 ms
  - 方案 B（`CSSStyleSheet` + `adoptedStyleSheets`）实施后复测：插入稳定 1.5 ~ 1.8 ms/200 条（首次 3.7 ms 为构造器冷启动），单次重算 ~0.2 ms（78 元素），无长任务——与方案 A 性能相当

### P1（待评估）：重算成本随规则数线性增长

- 未录制状态下实测：**12882 条规则 × 78 元素，一次全量重算仅 2.7ms**（约 100 万次匹配）；插入 200 条稳定在 ~1.2ms（无退化）
- 规则数继续上探至 **14882 条**：重算 ~~5ms（78 元素，每 +2000 条约 +2ms，线性增长），插入 200 条 1.6~~1.9ms，仍无退化
- 早期"3282 条 × 80 元素 = 17ms"是 DevTools Performance 录制态数据，录制会大幅放大重算耗时，不代表真实性能
- 主导因素是**元素数**而非规则数：同规则量下元素从 78 增到 1000，重算会放大 ~13 倍
- 缓解：按需实例拆分（规则合并不适用当前架构，见"优化方向"）

### P2（待改进）：测量工具

- 报告循环中插入后立即 `offsetHeight`，恰好触发 P0 的同步路径；修复后重算应恢复为独立耗时
- `getCSS()` 每次 O(n) 拼接，规则数大时统计本身有开销

### P3（已记录）：后台缓存回收导致回前台首次重算放大

- **现象**：标签页闲置（后台）一段时间后回前台，第一次交互的强制重算可达 20ms（正常 3~4ms），之后恢复
- **机制**：后台页面被节流，样式引擎的缓存（规则匹配索引）被回收；回前台第一次重算需重建全部规则（2.2 万条）的索引，一次性成本高
- **与 sheet 数量无关**：样式引擎按**总规则数**合并遍历所有 sheet，缓存重建成本 ∝ 总规则数，与 sheet 如何分配无关
- **非 roxcss 特有**：静态 CSS 大规则集同样存在；规则量小（几百条）时重建 <1ms，不可感知
- **缓解**：降低单实例总规则量（按需实例拆分）

### 最佳实践：预注册已知 token 集

**目标**：避免运行期动态插入新规则（每次插入都是一次样式失效，交互中触发重算）。

**做法**：应用启动时，把会使用到的 token 一次性注册：

```ts
// 启动时一次调用，批量注册全部已知 token（批量写入 = 一次解析 + 一次失效）
rox`p-4px m-2px w-100% flex-1 hover:bg-blue ...`;
```

后续交互若只使用已注册的 token，命中 `injected` 缓存，不产生插入和失效。

**边界（容易误用）**：

- **不能消除 P3 的回前台重建成本**：缓存重建 ∝ 总规则数，与规则何时插入无关
- **过度注册是负优化**：注册了用不到的 token 会膨胀总规则数，放大每次重算（和 P3 重建）的成本——注册集应等于实际使用集
- **动态 token 无法预覆盖**：值来自运行状态的 token（如 `rox\`p-${value}\``）只能覆盖已知值集合，新值仍会插入

## 六、优化方向（如需要）

> 注："规则合并"（多个 token 相同声明时合并为一条选择器列表）**不适用于当前架构**：缓存按 token 去重，合并需要额外的"声明 → token 集合"映射；已注入的规则无法原地修改，只能删除重插；合并后的选择器列表还会破坏"类名即 token"的 DevTools 可读性。

1. **按需实例**：不同路由/页面使用独立 rox 实例，减小规则集
2. **构建期预生成**：对已知类名做静态提取，运行时只兜底
3. **懒注入**：规则推迟到元素实际进入视口/挂载时插入
